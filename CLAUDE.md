# Работа над RC Planner

Локальное офлайн-приложение авиамоделиста: флот, чек-листы, полёты,
обслуживание, конфигурации. Без сервера, аккаунтов, аналитики и внешних
запросов. Vanilla HTML/CSS/JS, никаких зависимостей в рантайме.

Папка проекта: `~/projects/rc_planner`. Публикация: GitVerse Pages из `public/`.
Референс продуктовой философии — `~/projects/put-rebenka` (код и дизайн не копируем).
Планы и принципы продукта — `ROADMAP.md`; описание для пользователя — `README.md`.
Переосмысление дизайна 2.0 (аудит, направления, план) — `docs/redesign-2.0.md`,
техническое задание по решениям владельца — `docs/spec-2.0.md` (с
отступлениями при реализации по пакетам); исходники дизайн-канваса —
`docs/design/` (README там). Экраны с посеянными данными — набор
`test/seeded.js` (см. «Цикл выпуска»).

## ГЛОБАЛЬНОЕ ПРАВИЛО: безопасность и приватность (владелец, 2026-08-26)

Каждое изменение перед выпуском проходит аудит утечек данных:

- новых сетевых точек нет, либо они online-по-явному-действию, внесены
  в CSP и описаны на странице «Приватность» и в отчёте владельцу;
  локальные API (Wake Lock, View Transitions, popover) сетевыми точками
  не являются; Web Share (`saveFile`) — системный лист, приложение само
  ничего не отправляет, но пункт на «Приватности» о нём обязателен;
- пользовательские данные (модели, полёты, координаты, файлы) не покидают
  устройство; точная геопозиция наружу не уходит (для погоды — огрубление
  до ~1 км); внешним хостам — только referrer origin;
- XSS-дисциплина: пользовательский текст — через `esc()`, SVG — только
  `ICONS[key]`, координаты нормализуются в `loadAll`;
- каждый запуск code-review ОБЯЗАН включать угол «утечки данных
  в интернет / приватность» — вписывать это в задание ревью явно.

## Цикл выпуска

```bash
npm run icons     # только если менялся assets/icons/app-icon.svg
npm run build     # public/ (PWA) + dist/rc-planner.html (офлайн-файл)
npm test          # шесть наборов подряд, останавливается на первом упавшем
```

Порядок важен: `npm test` ничего не собирает. `test:audit` и `test:single`
читают `dist/rc-planner.html`, `test:pwa`, `test:visual` и `test:seeded` —
папку `public/`. Правка в `app.js` без `npm run build` не попадёт
в проверяемую сборку. `npm run release` делает всё по порядку.

Один набор — `npm run test:data|audit|single|pwa|visual|seeded` (`test:data` —
единственный без браузера). Скриншоты visual-набора падают в `test/shots/`,
seeded-набора — в `test/shots/seeded/` (папка чистится при каждом прогоне).
`test:seeded` — единственный набор, который проходит все экраны на
заполненной базе (аудит тоже сеет записи, но точечно — под XSS-пробы):
сеет три борта, четыре АКБ, 14 полётов, открытую работу, поддельный кэш
прогноза и копию 20-дневной давности; экраны («Сегодня» — в четырёх
состояниях дня) проходятся на телефоне в тёмной и светлой темах,
в перчатках и на 1280×800; проверяет
ошибки консоли, горизонтальную прокрутку, порог касания (44/52 px для всех
кнопок, `a.btn`, строк и селектов; токен `--seg` поднят до тех же 44/52,
исключений нет), «Взлёт» ровно на поле, «Посадку» на активном
полёте, баннер копии. Посев вымышленный, пилот — «Пилот»: настоящие имена
и позывной владельца в тесты не попадают. Новый экран или состояние —
добавить и сюда, иначе снимков не будет. Свежая машина:
`npm run setup` (ставит зависимости и chromium для Playwright), нужен Node ≥ 20.

Если изменение видно пользователю — новая запись в начало `data/changelog.js`
со своим `v` — **строкой**: версии уникальны, порядок задаётся положением
в списке, арифметики на `v` быть не должно (`'0.10' < '0.9'` как строки).
**Схема версий с 1.0** (решение владельца, 2026-08-25; выбор номера — на
усмотрение ассистента по этой шкале): `X.0` — крупный выпуск (переработка
раздела, пакет больших функций); `X.Y` — среднее обновление (новая функция,
заметное изменение UX — типичный «выпуск дня»); `X.Y.Z` — незначительное
(исправления, тексты, мелкие правки). Урок динамики 0.x: девять выпусков
за день — это нормально, но большинство из них должны были быть патчами
`X.Y.Z`, а не минорами; не раздувать средний номер. Первая запись показывается как «версия» в футере «Ещё». Просмотренную
версию `maybeWhatsNew` ищет по совпадению в списке: незнакомое значение (старый
формат, копия из будущего) — показать окно один раз. Без записи окно «Что нового»
не всплывёт. Записей держим не больше двенадцати, пункты — до 160 символов.
**Одна выкладка — одна запись:** пока сборка не отдана пользователям,
дописываем в верхнюю запись, а не заводим новую. В интерфейсе «модель»
называется «Борт» (решение владельца, 2026-08-25) — в новых текстах
только так; в коде идентификаторы model/aircraft остаются.

## Как устроено приложение

**`app.js`** — один файл, двенадцать пронумерованных разделов: состояние,
утилиты, статусы, данные, примитивы, экраны, действия, формы, навигация,
события, PWA, старт.

**Вкладки (2.0).** `TABS`: Сегодня · Флот · Полёт · Журнал · Ещё. «Сборы»
с панели ушли (решение владельца, 2026-09-01): экраны `packing`/`pack`
живут под «Сегодня», вход — карточка «Перед выездом» и строка в «Ещё».
«Сегодня» — один экран в четырёх состояниях `todayState()`: `home` (прогноз
из кэша, «Перед выездом», «К вылету», копия), `field` (герой — борт с
`takeoffReady()` и кнопкой «Взлёт»), `flying` (герой — полёт с живым
`#timer`), `debrief` (плитки дня, «Разобраться», полёты за сегодня);
разметка — `.today-main` + `aside.today-side`, от 900 px две колонки.
«Журнал» (`viewJournal`, `UI.journalTab` = `log|stats`, фильтр
`UI.journalAircraft`) вобрал прежние `log` и `stats` — их маршруты
остаются псевдонимами (`ROUTE_ALIAS`, разрешается один раз в `onRoute`,
не в рендерере — иначе сегмент на таком адресе мёртв); меню «⋯» — `popover="manual"`
через `toggleMenu`. Карточка борта — сегменты `UI.modelTab`
(`overview|components|maint|history`), сбрасывается при смене борта.
Экран полёта: «Посадка» (`land-flight`, ставит `landedAt`) отдельно от
итога (`finish-flight`), Wake Lock (`requestWakeLock`/`releaseWakeLock`)
держится только пока борт в воздухе и снимается в `paint()` через
`syncWakeLock()` при любой перерисовке не на экране полёта в воздухе
(посадка, отмена, уход с экрана; в `onRoute` его нет) и при возврате
вкладки из фона (`visibilitychange`).

**Экраны.** Экран — функция `view*()`, возвращающая строку HTML; карта
`RENDERERS` (id → функция), `TAB_OF` привязывает экран к вкладке нижней панели.
`render()` целиком заменяет `#views`; `render(true)` сохраняет прокрутку и фокус
(нужно для отметок в длинных списках). Переходы — `go(hash)`, маршруты вида
`#/model/<id>`. Новый экран — запись в `RENDERERS`, `TAB_OF` и в список `VIEWS`
в `test/audit.js`, иначе его никто не проверит.

**Движение (2.0).** `render()` — обёртка над `paint()` (прежнее тело
`render`): при поддержке `document.startViewTransition` и без
`prefers-reduced-motion` разметка меняется внутри перехода, направление —
`html[data-vt]` (`forward|back|tab` из `UI.navDir`, `update` для
`render(true)`). Следствие: код после `render()` на новый DOM рассчитывать
не должен (он появится в колбэке), а тесты после клика ждут результат
(`waitForSelector`/`waitForFunction`), не читают DOM сразу; `helpers.newPage`
по умолчанию гасит анимации (`reducedMotion: 'reduce'`), `RCP_MOTION=1`
включает их. Окна закрываются через `closeModal()` с классом `closing`
и удалением узла по `transitionend`; `openModal` зовёт `closeModal(true)`.
Живой таймер, Wake Lock и восстановление фокуса живут внутри `paint()`.

**События.** Обработчиков на элементах нет: разметка пересобирается целиком,
поэтому `click`/`submit`/`change` висят на `document`, элементы помечены
`data-nav`, `data-act`, `data-form`, `data-change`. Действия — в `ACTIONS`,
формы — в `FORMS`.

**Данные.** Пользовательские данные — IndexedDB через `db.js` (обёртка без
зависимостей); снимок целиком живёт в `S`, после записи store перечитывается.
Blob (фото, файлы конфигураций) хранятся прямо в IndexedDB; в экспорт уходят
как base64 (`__blob`). Новые store добавлять в `STORES` в `db.js` (+ миграция
по версии) и в snapshot/экспорт ничего — он универсальный. localStorage —
только UI-предпочтения: `rcp.theme` (`light`|`dark`; нет ключа — по
системе, `applyTheme()`), `rcp.gloves` (`1` — режим «В перчатках»,
`html[data-gloves]` переопределяет токены размеров в `styles.css`),
`rcp.hi` (приветствие), `rcp.seen` (просмотренная версия), `rcp.seeded`
(стартовые сборы посеяны), `rcp.tour` (обучение заново). Всё остальное —
IndexedDB (в том числе `settings.lastBackupAt` и кэш прогноза); основной
базой localStorage не является.

**Справочный контент** (не пользовательские данные) — `data/*.js`:
чек-листы, каталог инструментов, стартовые сборы, changelog. Чтобы поправить
текст, трогать код не нужно. Инварианты данных стережёт `test/checks.js` —
самый быстрый набор, браузер ему не нужен.

**Экранирование.** Весь пользовательский текст в HTML — только через `esc()`.
Аудит гоняет XSS-пробу; новую вставку без `esc()` он поймает не всегда —
следить руками.

**Сборка.** `build.js` вклеивает CSS, `db.js`, `data/*.js` и `app.js` в HTML
по маркерам `<!-- build:… -->` и делает два выхода: `public/` с manifest, sw
и иконками и `dist/rc-planner.html` без PWA (по `file://` service worker
не работает; регистрация SW в рантайме дополнительно ограждена протоколом).
Версия — sha1 сборки; подставляется в `sw.js` и `<meta name="build">`, откуда
её показывают настройки. Сборка падает при внешних ресурсах, битом manifest
и иконках старше SVG.

## Правила, за которые уже заплачено (наследие референса)

- **Обновления.** Навигация в SW — из сети, кэш запасной; регистрация
  с `updateViaCache: 'none'`. В `install` **нет** `skipWaiting()`: управление
  передаётся только по кнопке «Обновить». `controllerchange` перезагружает
  страницу лишь когда контроллер уже был — при первой установке событие
  тоже приходит.
- **Окна.** Одно модальное окно за раз (`openModal` сам закрывает прежнее).
  Не полагаться на `::backdrop` — блокировка фона своя (`body.locked`).
  Закрытие по кнопке, Esc и фону идёт через `dismissModal()`: он возвращает
  прерванную форму из `UI.modalReturn` (сценарий «+ Добавить локацию» из итога
  полёта). Внутри `openModal` остаётся именно `closeModal()` — иначе рекурсия.
  Стэш хранит значения через `FormData`, поэтому не годится для форм с файлами
  (фото модели).
- **Числа в формы — через `numVal()`** (урок ревью 1.4). `validateBackup`
  проверяет только `id` записей, поэтому значения полей из импортированной
  копии произвольны, а `value="${…}"` в шаблонах формы не экранируется:
  строка вида `" onfocus="…` вырывалась из атрибута и исполнялась
  (подтверждено живой пробой). Любое числовое поле формы — только
  `value="${numVal(x)}"`. Аудит гоняет эту пробу по формам борта и АКБ
  и проверяет DOM-атрибуты, а не регулярку по `innerHTML`: экранированная
  кавычка в тексте `<option>` при сериализации выглядит сырой и даёт
  ложную тревогу.
- **Иконки.** Все SVG лежат в `ICONS` и вставляются ТОЛЬКО как `ICONS[key]`
  (третий аргумент `rowBtn` — ключ, не разметка). Пользовательские строки
  в SVG-слоты не попадают; аудит такую ошибку не поймает.
- **Имена файлов — латиницей**: macOS хранит имена в разложенной форме Unicode,
  после распаковки git видит «двойники».
- **Не подключать CDN, шрифты и картинки по сети** — приложение обязано
  работать офлайн; сборка это проверяет. Это про ресурсы самого приложения:
  online-API (погода) допустимы, но только по явному действию пользователя,
  с пометкой «online», честным сообщением офлайн и записью в CSP `connect-src`.
  Исключение того же рода — мини-карта локаций (`openMapPicker`): тайлы
  tile.openstreetmap.org создаются через `createElement('img')` (литерал
  `<img src="http…` сборка бы зарубила), CSP `img-src` расширен точечно,
  атрибуция «© OpenStreetMap» обязательна, тайлы не кэшировать пачками
  (usage policy OSM).
- **Прошивки Walksnail — ручной список** (`data/firmware.js`, с 1.5).
  Показываем только последнюю известную версию и ДАТУ СВЕРКИ. Почему
  не живой запрос: Google Диск (единственный канал раздачи этих прошивок)
  не отдаёт `access-control-allow-origin` — браузер не даст приложению
  прочитать папку; у `api.github.com` заголовок есть, но репозиторий
  CaddxFPV-Tech отстаёт от Диска и не подтверждён с сайта производителя
  (замер 2026-08-30). Обновление — по команде владельца «обнови прошивки»:
  список файлов читается через `drive.google.com/embeddedfolderview?id=…`,
  версии сортируются ЧИСЛЕННО по сегментам (строкой `38.43.4` окажется
  свежее `38.43.13`). Ссылки на конкретные версии брать из каталога папки,
  а не с вики: там ссылка «18.21.10 (Latest)» ведёт в папку с 17.5.8.
  Инварианты файла стережёт `test/checks.js` (без `source` экран
  «Инструменты» падал целиком).
- **Ссылки наружу** (каталог инструментов) — только официальные источники,
  `target="_blank" rel="noopener noreferrer"`, пометка «online». Чужие прошивки
  не распространяем — только ссылки на релизы производителей.
- **Подготовка бортов.** `a.prepared = {runId, at, siteId}` — одноразовая
  пометка «чек-лист пройден» (кнопка «Готов»); гаснет при взлёте
  (`takeoff()`) и при полёте с проблемой. Взлёт подготовленного — без
  повторного чек-листа, через `takeoff-prepared`. Кнопка «Взлёт»
  показывается ТОЛЬКО через `takeoffReady()`: подготовка свежая
  (`preparedFresh` — до конца дня МСК), нет запрета/обслуживания,
  нет активного полёта. Обходить этот гард нельзя.
- **Цепочка после краша**: полёт с проблемой → авто-осмотр (открытая
  работа, статус «Обслуживание») → «Выполнено» → снова «Готов».
  `statusOf` держит «Проверить» только пока НЕТ закрытой работы новее
  проблемного полёта — не ломать эту логику.
- **Группы флота** — `settings.fleetGroups` [{id, name, parentId}] +
  `a.groupId`; вложенность строго один уровень (подгруппой может стать
  только группа без подгрупп). Перенос борта — модалкой в два касания,
  НЕ drag-n-drop (осознанно: тач в полевых условиях). Сортировка
  `settings.fleetSort` работает внутри групп и не трогает их порядок.
- **Вертолёты не планируются** — решение владельца.

## Context7 — когда обязателен, а когда не нужен

Решение владельца (2026-08-23, уточнено 2026-08-24): Context7 используется
всегда, когда код опирается на внешнее знание, и НЕ используется там,
где он бесполезен, — лишние запросы тоже ошибка.

**Обязателен перед кодом, который трогает:**

- внешние API и сервисы (Open-Meteo и т.п.) — параметры и лимиты сверить
  через Context7 **и** подтвердить живым запросом (`curl`), потому что
  документация и реальность могут расходиться;
- API библиотек и dev-инструментов (sharp, playwright и любые новые);
- малознакомые браузерные API при первом использовании в проекте;
- ссылки каталога `data/tools.js` — сверка с официальной документацией.

**Не нужен (не тратить запросы):**

- собственная логика приложения: экраны, расчёты, `esc()`, роутинг;
- вёрстка HTML/CSS, тексты, changelog, правки данных в `data/*.js`;
- проверка живости ссылок — это curl/WebFetch, Context7 этого не умеет.

**Проверка ссылок** (всегда, Context7 тут только для сверки с доками):
HTTP 200 + заголовок/содержимое страницы соответствуют назначению
(`curl … | grep -i "<title>"` или WebFetch) + ресурс известен сообществу.
Урок 2026-08-24: adamone.rchomepage.com отдавал 200, но вёл на вредоносную
страницу — код ответа ничего не гарантирует. Дату последней проверки
обновлять в шапке `data/tools.js`. Ссылку, которую невозможно проверить
из текущей сети (гос-сайты), не добавлять самому — предложить владельцу
проверить и добавить после его подтверждения.

Если Context7 недоступен — сказать прямо и пометить непроверенное.

## Окна для полётов: как считаются пороги

Логика (решение владельца, 2026-08-24): **модель → место → дата → окна**.
Ограничения выводятся из ТТХ модели, а не берутся константой:

- порог ветра — `a.maxWind`, а без него оценка `wxEstimate(a, battWeight)`:
  от ПОЛНОГО веса (сухая модель + выбранная на экране АКБ) и габаритов
  (квад с диагональю >300 мм — минус 4). Шкала для опытных пилотов, базы
  16–20 м/с; калибровка по парку владельца — в комментарии к функции.
  Веса платформ в `data/presets.js` — СУХИЕ, без АКБ; вес АКБ — поле
  батареи (`battEstimateWeight` оценивает по химии и ёмкости);
- высота полёта — `a.maxAlt` (потолок поля — 200 м); 200 м — это высота
  полёта, а не «проверять ветер всегда до 200 м»: уровни ветра Open-Meteo
  (80/120/180 м) берутся только в пределах высоты полёта модели
  (`wxLevels()`), низколетящий квад не бракуется ветром на 180 м;
- ночь полёты НЕ запрещает (решение владельца, 2026-08-25): сложные
  условия снижают порог через `wxDifficulty()` (ночь ×0.8, туман ×0.75,
  морось ×0.85, слабый снег ×0.8, перемножаются); жёсткие запреты —
  `wxHardStop()`: явный дождь (≥0.2 мм или коды 63+), снегопад, метель
  (снег при ветре >8), гроза, туман ночью;
- порывы — до 1.4 эффективного порога; окна — подряд часы без «bad»,
  все 24 часа;
- прогноз — ориентир, решение о вылете всегда за пилотом (дисклеймер
  в интерфейсе не убирать);
- **время всегда по МСК** (решение владельца, 2026-08-25): запрос с
  `timezone=Europe/Moscow` (`WX_TZ`), «сегодня» для привязки к дням —
  `wxTodayISO()`, не `todayISO()`;
- индекс дня привязывается к датам из ответа API, не к «сегодня + N»,
  иначе вчерашний кэш сдвигает дни.

Менять пороги и эвристики — только в разделе «Окна для полётов» в `app.js`:
`wxEstimate`, `wxLevels`, `wxDifficulty`, `wxHardStop`, `wxVerdict`.
Коэффициенты — ТОЛЬКО через константу `WX_K`: из неё же строятся таблицы
`wxHelpHtml()`, расчёт и объяснение разойтись не могут. `wxHardStop`/
`wxDifficulty` считаются один раз в `wxDay` (`hr.stop`, `hr.diff`) —
строка часа читает готовое.

## Чего не делать

- Не тащить зависимости в рантайм (`sharp` и `playwright` — только dev).
- Не заводить серверную БД, аккаунты и обязательную синхронизацию.
- Не переписывать проект целиком ради стиля — менять минимально необходимое.
- Не использовать localStorage как основную базу.
